AI-Assistant: Architecture Plan

Version 2 · 2026-10-19 · For Andrew · Repository: Andrewoh2020/AI-assistant · Supersedes the first draft (Claude Doc, same date)

We build a personal agent modeled on Meta's Muse, web first and mobile second. A TypeScript backend of our own sits between the user and every outside service. Travila runs the agent, Browser Use is the browser, and DeepSeek's Search API, called directly, is the search engine. The first feature we ship is Everyday Q&A, research and explanations, but the architecture and data model below cover every Muse feature, so later features add tables and screens without reworking what exists.

2. Languages and frameworks

Recommendation: TypeScript for all three parts (web, mobile, backend). One language means shared types, one API client and one set of design tokens, and it is the language coding agents are most reliable in.

OptionWhat it isFit for this project
React (Next.js)The standard way to build web appsChosen for web. It is not an alternative to Expo: React is for the browser, Expo is React for phones
Expo (React Native)React for iOS and Android, rendering real native controlsChosen for mobile. Shares TypeScript, the API client, data types and tokens with the web app. Native controls match the spec's "native, not branded-loud" rule (iOS sheets, system type)
FlutterGoogle's toolkit in the Dart language, drawing its own pixelsGood for identical-looking apps, but it is a second language beside the web code, it imitates native controls rather than using them, and its web output is weaker for text selection and accessibility
RustA fast, memory-safe systems languageCoding agents can write Rust, but iteration is slower and fixes take more rounds. Our backend mostly waits on Travila, Browser Use and the search API, so Rust's speed buys nothing now. Worth revisiting only for a sandbox or high-throughput component later

Skills and subagents

Muse's skills (54 playbooks) map to Travila agent profiles plus prompt fragments: a small always-loaded core and a searchable catalog loaded on demand. Subagents (research fan-out, artifact builds, the browser agent) are separate profiles that run their own Travila threads, never talk to the user, and return one report to the main run. Depth is limited to one level of delegation.

5. One Q&A turn, step by step

  1. The user sends a question. The session gate confirms who they are and that the chat is theirs.
  2. The orchestrator sends the turn to Travila (send-message) with the user's Travila id, the main agent profile, the current date table in the user's timezone, and the tool list. Travila adds relevant memories automatically.
  3. The model asks for a tool, for example web_search. The run pauses with AGENT_STATUS_AWAITING_CLIENT_TOOLS; the orchestrator hands the call to the tool runner.
  4. The policy gate checks the call, runs it (DeepSeek Search for search, a plain HTTPS fetch or DeepSeek Fetch for pages), wraps results as EXTERNAL CONTENT, and records each URL in sources.
  5. If a page needs JavaScript, a login, an upload or a download, the model calls browse; the worker starts a Browser Use run and the live view appears in the detail pane.
  6. Results go back to Travila (submit-client-tool-results); steps 3 to 5 repeat until the run completes. The client shows status lines ("Searching", "Reading 3 pages").
  7. The reply arrives whole. Text parts become the answer; reasoning parts (picked by type, not position) go in the collapsed "How I worked this out" section and are shown as plain text with no clickable links. Any URL not in that run's sources is removed and logged; numbered citations sit beside each claim with a Sources list at the end of the answer; facts the user stated are saved to memory.

Why we run search ourselves: a model only knows what it learned in training, cannot see today's web, and cannot cite a page it has not read. Travila documents no built-in search tool, and Browser Use would need a full browser session for each search, which is slower and costs more. A search API returns results in one call; Browser Use is kept for pages that need a real browser.

Not available from Travila today, per its docs and Travila's own answer: word-by-word streaming (we poll), a web search tool (we run our own), Qwen models (Travila adds them on request), bulk memory deletion (our forget flow deletes record by record), and per-user secret storage (Travila secrets are per project, so user passwords go in our vault).

Browser Use

  • API v4 at https://api.browser-use.com/api/v4, key in X-Browser-Use-API-Key, read from BROWSER_USE_API_KEY.
  • Used only when a plain fetch is not enough: JavaScript pages, logins, uploads, downloads, multi-step flows.
  • One profile (cookies, sign-ins) and one workspace (input and output files) per user. Download links expire after 60 seconds, so the worker copies results into our files store immediately.
  • Live view URL shown only to its owner and treated as a credential.
  • Chosen over Browserbase (cannot accept uploaded input files) and Firecrawl (downloads disappear when the session ends).

Search: DeepSeek Search API (direct), Brave as backup

DeepSeek offers web search in two ways. We use the second.

  • Built into the model (a server-side web_search tool in DeepSeek's own Responses API at api.deepseek.com). Not used: it only works with deepseek-v4-pro and is ignored by Flash, Travila sends our turns through its own API so there is no documented way to switch it on, it would bypass our policy gate and source log, and the Sonnet backup would lose search whenever it takes over.
  • Standalone Search and Fetch APIs (released 2026-10-17). Search returns title, URL, summaries, optional full text, publish date and an authority rating, 1 to 50 results per query (queries up to 128 characters). Fetch returns one page as Markdown. About $0.75 per 1,000 successful calls each; empty results and failures are free; 5 requests per second each. Decided: we use these (Andrew, 2026-10-19). Every query still passes our policy gate, every URL lands in sources, and search works no matter which model answers.

How we call it (decided 2026-10-19). Travila does not offer DeepSeek Search today (Ian: "a good request, we'll discuss it"). So our tool runner calls DeepSeek directly with our own key:

  • Search: POST https://api.deepseek.com/v1/tools/search with query (up to 128 characters, supports site:, after:, before:), count (1 to 50, default 10), optional ori_question and need_content. Each result has title, URL, snippet, summary, optional content, date, site name, authority (0 to 4) and rerank_score (0 to 3; 1.5 and up is high quality).
  • Fetch: POST https://api.deepseek.com/v1/tools/fetch with url; returns title and Markdown. DeepSeek's servers do the fetching, so private-network (SSRF) risk stays off our infrastructure; the policy gate still checks the URL first.
  • Auth: Authorization: Bearer <key>, held as a network secret for api.deepseek.com, never in code or chat. Limits: 5 requests per second each, HTTP 429 when exceeded, so the tool runner queues and retries.
  • Trade-off: search is billed by DeepSeek, not through Travila. If Travila adds it later, we switch the backend behind web_search without touching anything else.

Queries pass the policy gate's discretion check so private details from memory are not sent to the search engine. The search backend sits behind one interface, so switching to Brave is a configuration change, and the evals compare both.
